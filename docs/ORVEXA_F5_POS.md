# Orvexa F5 — POS, payments, receipts and refunds

Implemented 2026-11-14 against the updated sibling Spring project. F0–F5 implement the requested MVP feature phases; F9 production-readiness work remains. F6–F8 are post-MVP. This phase stops for review.

## Screens and behavior

- `/app/pos`: permitted-branch scanner/exact SKU or barcode lookup, search/pagination, sellable variants, base or configured sale units, basket editing and removal. F2 focuses the scanner; F8 opens checkout review. Enter submits a scan. Conversion quantities stay decimal strings; the server validates whole base-unit conversion. Repeated scans increment base units; a line using a conversion unit asks the cashier to review its quantity instead of guessing another pack.
- The server supplies current branch prices, applicable automatic/manual discounts, classifications, rates and net/tax/total. Management-only manual discounts require a reason. The greatest applicable percentage applies once. The frontend never calculates authoritative money, tax, inventory, refund or cost balances. Unsafe JS integer amounts block payment/reservation rather than display rounded totals.
- Preview does not reserve stock. Confirmation creates an idempotent five-minute reservation, navigates to its saved record and requires another explicit payment confirmation. Insufficient stock and stale/conflicting prices require correction/refresh. Branch changes clear the basket; saved orders retain their recorded branch.
- `/app/orders/:id`: saved amounts and tax snapshot, expiry countdown, attempts and lifecycle events. The browser countdown is advisory; Spring remains authoritative. Expired unpaid reservations cannot start payment. UNKNOWN/PENDING attempts retain their hold after normal expiry and offer neither a new payment nor unpaid cancellation.
- Cash records staff confirmation of received funds. Manual terminal creates an UNKNOWN hold; it does not charge a bank or accept card data. Owner/Administrator/Manager can reconcile CONFIRMED, DECLINED or externally verified VOIDED using an external reference. Fulfillment requires the backend's inventory/management role; a Cashier does not gain that authority.
- The tenant development simulator is hidden unless `VITE_SHOW_PAYMENT_SIMULATOR=true`. The server must independently enable it in its permitted development/demo/test profile. Public storefront checkout remains explicitly simulated and uses its separate public order token.
- Payment, reconciliation and reversal confirmations require acknowledgement. An ambiguous transport/5xx/408 result freezes the operation. Check saved state first; retry only the exact original command and request ID when still needed. Uncertain financial dialogs retain the command and cannot close until reconciled. A failed retry remains blocked. Offline writes are rejected by the transport; reconnecting refreshes quote/order/payment state before payment is enabled again.
- Walk-in sales need no customer account. Confirmed-sale receipt email is optional. The backend checkout DTO has no customer-link field, so customer linkage is not invented in the UI.

## Receipts and reversals

Confirmed payments unlock original saved receipts. Preview uses server text escaped into a sandboxed, script-free iframe with a white print surface and dark logo. The print button invokes browser printing; PDF/HTML/text downloads are generated by Spring. Receipt email queueing explicitly reports that delivery is unconfirmed.

A paid sale supports quantity-based reversal requests. Physical RETURN is available after fulfillment with an explicit resellable choice. REFUND never restocks. CANCEL includes every remaining unfulfilled unit and restores that stock on completion. Pending/approved/completed requests consume their units; rejected requests do not. Remaining quantities are a UI constraint from saved records; Spring rechecks them transactionally and calculates historical refundable amounts.

Request → management approve/reject → explicit actual refund completion. Cash refunds record CASH; externally verified terminal refunds require EXTERNAL_MANUAL plus a reference; simulator refunds use SIMULATED. Completion records an outcome and does not transfer bank funds. Original batch/cost restoration and refundable limits remain server controlled. The original receipt is unchanged by reversals.

## Limits and release handoff

There is no saved-order lookup by reservation request ID, and history omits payment state. If an initial reservation response is lost, keep the current basket/command, inspect recent orders, then use the unchanged idempotent command to recover the saved record. After reload/session loss the in-memory command ID is gone: inspect history and resolve existing holds or let eligible unpaid reservations expire before recreating a sale. Do not identify an order only by matching its total. No offline checkout queue is implemented.

Receipt email has no per-order delivery-status read; a lost queue response can only be retried with the original command after checking saved state, and delivery remains unconfirmed. Backend PDF glyph support is limited; browser print/HTML preserve Unicode. Physical return quantities use sold base units, even if the original sale used packs. No customer linkage, coupon builder, split tenders, automated terminal adapter, or marketing consent flow is implied.

Recommended next step for the MVP is **F9 accessibility, production readiness and handoff**, followed by release review. **F6 CRM/loyalty/promotions/notifications** is the next numbered feature phase and is explicitly post-MVP. Stop here for phase review before either expansion.
